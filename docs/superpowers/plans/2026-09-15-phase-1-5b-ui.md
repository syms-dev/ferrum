# Phase 1.5b — the web UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `ui/` — the schema-driven single-page UI an operator actually uses — plus the four read-only ferrumd endpoints it cannot be built without. At the end of this plan a real operator on a real booted host can log in over HTTP, see the real app catalog rendered from the real built schema, change a setting, trigger a real apply, watch it stream, and roll back to a real prior generation from a confirmation dialog that tells the truth about what reverts.

**Architecture:** ferrumd gains four `GET` endpoints behind its existing `require_session` middleware (`/api/catalog`, `/api/generations`, `/api/jobs`, `/api/session`) plus a static-file handler with an SPA fallback. `journal`/`generations` move out of the `ferrum-apply` binary crate into a new shared `ferrum-state` library crate so ferrumd can import them — mirroring Phase 1.5a's own `ferrum-secrets` extraction. `ui/` is hand-written HTML/CSS/ES modules with **no build step and no npm**, packaged by a `runCommand` and pointed at by a new `FERRUM_UI_DIR`.

**Tech Stack:** Rust (`crates/ferrumd`, `crates/ferrum-state`, axum — following the existing handler/env-var conventions), Nix (a new `nix/pkgs/ferrum-ui`, a new eval check following the existing `mkAssertionCheck` pattern), vanilla ES modules (no framework, no bundler, no dependencies).

**Spec:** `docs/superpowers/specs/2026-09-15-phase-1-5b-ui-design.md`

## Global Constraints

- **No new mutation, no new privileged capability.** `POST /api/jobs`, `PUT /api/settings` and `POST /api/secrets/:name` remain the complete set of state-changing operations. Every endpoint this plan adds is a `GET`. The polkit rule, the `ferrum-apply@.service` template unit, and the closed `JobRequest` enum are all untouched — if a task finds itself editing any of them, it has gone outside this plan.
- **`ReadWritePaths` in `modules/core/daemon.nix` does not change.** The two new paths ferrumd reads (`/nix/var/nix/profiles/`, `ferrum.storage.journalDir`) are read-only; `ProtectSystem = "strict"` makes the filesystem read-only, not invisible, so no directive is added. A task that finds itself widening `ReadWritePaths` has made a mistake.
- **No new entry on ferrumd's `path`.** It is `[ pkgs.sops pkgs.ssh-to-age ]` and stays that way — this is the concrete reason the generations endpoint reads the profile directory instead of shelling out to `nix-env` (which would drag `config.nix.package` onto an unprivileged network-facing daemon's PATH).
- **The UI never hardcodes an app, an option name or a field type.** Adding a directory under `modules/apps/` must make the app appear with zero `ui/` changes. Task 8's eval check is the mechanical guard on this; a task that hardcodes `"sonarr"` anywhere in `ui/` has broken the phase's central claim.
- **`Cargo.lock` must be regenerated when `ferrum-state` is added** and committed in the same commit as the new crate. This repo has taken a CI failure for exactly this twice (`f86c90f`, `402c8be`).
- **Confirmed real, read directly from the code before this plan was written** (do not re-derive, but do re-verify if a task's edit disagrees):
  - `crates/ferrumd/src/db.rs` creates **three** tables — `users`, `sessions`, `login_attempts`. There is **no `jobs` table**, contrary to the 1.5a spec's description. Job state is the JSONL files plus `AppState.job_running`. This plan does not add one.
  - `crates/ferrum-apply/src/generations.rs` already contains `parse_nix_env_list`, `correlate`, `is_rollbackable` and `GenerationInfo`, all tested, all carrying `#[allow(dead_code)]` comments that name "a future ferrumd-facing API" as their intended consumer.
  - `crates/ferrum-apply/src/journal.rs` already contains `list`/`read`/`write` and `JournalEntry`, with `list`/`read` likewise `#[allow(dead_code)]`.
  - `crates/ferrumd/src/main.rs:122` declares `const CSRF_HEADER: &str = "X-CSRF-Token"`, and `crates/ferrum-apply/src/request.rs`'s `Request` enum is `#[serde(rename_all = "snake_case")]` over `preflight`/`apply`/`rollback`/`restore_state`/`gc` — these are the exact kind strings Task 4's `started` event must emit.
  - `modules/core/daemon.nix` sets `FERRUM_SETTINGS_SCHEMA` but **not** `FERRUM_CATALOG`; `nix/modules/flake/packages.nix` builds `ferrum-catalog` and its own header comment says "Nothing consumes this yet."
  - `ferrum.storage.journalDir` (`modules/core/options.nix:39`, default `/var/lib/ferrum/journal`) has **no** `systemd.tmpfiles` rule — it is created incidentally by `journal::write`'s `create_dir_all`.
  - `crates/ferrumd/src/main.rs`'s `method_is_mutating` already exempts `GET` from the CSRF check, so no new endpoint needs CSRF handling.

## Task 1: Extract `crates/ferrum-state` from `ferrum-apply`

**Files:**
- Create: `crates/ferrum-state/Cargo.toml`, `crates/ferrum-state/src/lib.rs`
- Move: `crates/ferrum-apply/src/journal.rs` → `crates/ferrum-state/src/journal.rs`
- Move: `crates/ferrum-apply/src/generations.rs` → `crates/ferrum-state/src/generations.rs`
- Modify: `crates/Cargo.toml` (workspace members), `crates/ferrum-apply/Cargo.toml`, `crates/ferrum-apply/src/main.rs`, and every `ferrum-apply` file importing `crate::journal`/`crate::generations` (`apply.rs`, `rollback.rs`, `restore_state.rs` — confirm by grep, do not assume the list)
- Regenerate: `crates/Cargo.lock`

**Interfaces:**
- Produces: `ferrum_state::journal::{JournalEntry, snapshot_name, write, read, list}` and `ferrum_state::generations::{GenerationInfo, parse_nix_env_list, correlate, is_rollbackable}`.

This is a refactor of shipped, reviewed, production-tested code — the single largest risk in this plan (1.5a known risk 3, which materialised as real rework during the `ferrum-secrets` extraction). **The tests move with their modules, intact.** Do not rewrite them, do not "modernise" them, and do not drop one because it looks redundant after the move.

- [ ] **Step 1: Create the crate and move both modules verbatim**

`git mv` both files so the move is visible as a move in history rather than a delete-plus-add. Change only what the move forces.

**One visibility change is required and is already confirmed:** `generations::snapshot_ts` is declared `pub(crate)` (`generations.rs:51`) and has a real caller in `rollback.rs:1,29`, which stays in `ferrum-apply`. After the move that call crosses a crate boundary, so `snapshot_ts` must become `pub`. Do not resolve this by copying the function into `rollback.rs` — two implementations of "which snapshot is newest" is exactly the drift this extraction exists to prevent.

`Cargo.toml` mirrors `crates/ferrum-secrets/Cargo.toml`'s shape exactly (same edition, same workspace inheritance style). Dependencies are whatever the two moved modules really use: `serde`, `serde_json`, `anyhow`.

- [ ] **Step 2: Remove the now-wrong `#[allow(dead_code)]` attributes**

Every `#[allow(dead_code)]` in the moved code exists because the item had no caller *within the `ferrum-apply` binary's call graph from `main()`*. In a library crate, a `pub` item needs no such allowance, and leaving the attributes on would suppress a genuine future dead-code regression. Remove them, and remove the comments that explain them (`"kept for a future list-generations consumer"` and friends) — that future has arrived and the comments are now false. Replace the `GenerationInfo` field comment with a plain statement that `date`/`current` are what the generations API reports.

- [ ] **Step 3: Point `ferrum-apply` at the new crate and regenerate `Cargo.lock`**

Add `ferrum-state` to `crates/Cargo.toml`'s `members`, add the path dependency to `crates/ferrum-apply/Cargo.toml`, drop the two `mod` declarations from `main.rs`, and rewrite the imports. Then regenerate `Cargo.lock` — **this cannot be skipped and cannot be hand-edited.**

**Verification:** `cargo test -p ferrum-state -p ferrum-apply` passes with the same number of tests as before the move (count them first), `cargo clippy --workspace --all-targets -- -D warnings` is clean, and `git diff --stat` shows no test was lost.

## Task 2: `GET /api/catalog`

**Files:**
- Create: `crates/ferrumd/src/catalog.rs`
- Modify: `crates/ferrumd/src/main.rs` (declare the module, add the route to `protected`), `modules/core/daemon.nix` (add `FERRUM_CATALOG` to `environment`), `nix/modules/flake/packages.nix` (update the now-false "Nothing consumes this yet" header comment)

**Interfaces:**
- Produces: `GET /api/catalog` → `{ schemaVersion, ferrumVersion, apps, schema }`.

- [ ] **Step 1: Write the handler**

Read `$FERRUM_CATALOG` and `$FERRUM_SETTINGS_SCHEMA`, parse both as JSON, and merge the schema in under a `schema` key of the catalog object. Follow `settings.rs`'s established error style **exactly** — a missing env var, an unreadable file, and unparseable JSON each produce a distinct `500` naming the real path, because "the catalog is empty" rendering as "this host has no apps" is the failure this must never produce silently.

Read per request rather than caching at startup, for the reason `settings.rs` already documents for the schema: a ferrumd left running across a generation switch must not serve a catalog its own binary no longer matches. State this in a comment so a future reader does not "optimise" it into a `OnceCell`.

- [ ] **Step 2: Wire `FERRUM_CATALOG` in `modules/core/daemon.nix`**

`FERRUM_CATALOG = "${pkgs.ferrum-catalog}/share/ferrum/catalog.json";`, placed alongside the existing `FERRUM_SETTINGS_SCHEMA` line. Both are store paths; ferrumd reads them under `ProtectSystem = "strict"` without any new directive.

- [ ] **Step 3: Unit tests**

Env-var-driven, using `tempfile` and the serialized-env-mutation pattern `settings.rs`'s own tests already use (that file's tests mutate process-wide env; follow the same discipline so they do not race): a real catalog file and a real schema file merge into the expected shape; a missing `FERRUM_CATALOG` is a 500 naming the variable; a catalog file containing invalid JSON is a 500 naming the path, not an empty app list.

**Verification:** `cargo test -p ferrumd` passes. Task 8's VM test proves it against the really-built catalog.

## Task 3: `GET /api/generations`

**Files:**
- Create: `crates/ferrumd/src/generations.rs`
- Modify: `crates/ferrumd/src/main.rs`, `crates/ferrumd/Cargo.toml` (depend on `ferrum-state`), `modules/core/daemon.nix` (add `FERRUM_PROFILES_DIR`, `FERRUM_JOURNAL_DIR`), `modules/core/storage.nix` (tmpfiles rule for the journal directory)

**Interfaces:**
- Produces: `GET /api/generations` → `{ current: u32|null, generations: [{ generation, date, current, snapshot, rollbackable, reason }] }`.

- [ ] **Step 1: Read the profile directory**

`list_profile_generations(dir: &Path) -> anyhow::Result<Vec<(u32, String, bool)>>`. `/nix/var/nix/profiles/` holds `system-<N>-link` symlinks plus a `system` symlink pointing at the current one. Read the directory, parse `N` out of each matching name, resolve `system`'s own target to identify the current generation, and take each link's date from its **`symlink_metadata` mtime** (`lstat`, not `stat` — `stat` follows through to the store path, whose mtime is the Nix epoch and is the same for every generation; this is the single easiest way to get this task subtly wrong).

Format dates as `"%Y-%m-%d %H:%M:%S"`, the exact shape `ferrum_state::generations::parse_nix_env_list` produces, so the two readers of this data agree on one format. Return sorted descending by generation number.

Entries that do not match `system-<N>-link` are skipped silently — `/nix/var/nix/profiles/` legitimately contains other profiles (`per-user`, and `system-profiles/` on some hosts) and encountering one is normal, not an error.

- [ ] **Step 2: Correlate with the journal and build the response**

Call `ferrum_state::journal::list($FERRUM_JOURNAL_DIR)` and `ferrum_state::generations::correlate`, then map each `GenerationInfo` through `is_rollbackable`: `Ok(())` → `rollbackable: true, reason: null`; `Err(msg)` → `rollbackable: false, reason: msg`. **Serialise the crate's own message verbatim** — the UI displays it. Do not paraphrase it into a second vocabulary for the same condition.

A journal directory that does not exist yields an empty list (`journal::list` already returns `Ok(vec![])` for a missing directory — confirm this is still true rather than assuming), which correctly renders as "every generation exists, none is rollbackable," not as an error. A host that has never applied through `ferrum-apply` is a real, valid state.

- [ ] **Step 3: Wire the two env vars and the tmpfiles rule**

In `modules/core/daemon.nix`: `FERRUM_PROFILES_DIR = "/nix/var/nix/profiles";` and `FERRUM_JOURNAL_DIR = ferrum.storage.journalDir;` (read from the real option, never hardcoded — an operator who moved it must not silently get an empty rollback list).

In `modules/core/storage.nix`, add to the existing `systemd.tmpfiles.rules` list:
```nix
"d ${cfg.journalDir} 0750 root ${ferrumdGroup} - -"
```
Reuse that file's existing `ferrumdGroup` binding — it already falls back to `root` when `ferrum.daemon.enable = false`, precisely so naming a nonexistent group cannot fail tmpfiles at boot, and its own comment warns that two rules for one path is a conflict rather than a merge. Check there is no existing rule for this path before adding one.

- [ ] **Step 4: Unit tests**

Against a real temp directory built to look like a real profile directory: several `system-<N>-link` symlinks with distinct mtimes plus a `system` symlink, and confirm the right generation is marked `current`; a directory containing `per-user` and other non-matching entries, and confirm they are skipped rather than erroring; the `rollbackable`/`reason` mapping for a generation with a snapshot and one without; an absent journal directory yielding a list where nothing is rollbackable.

**Verification:** `cargo test -p ferrumd` passes; clippy clean.

## Task 4: `GET /api/jobs` and `GET /api/jobs/:id`

**Files:**
- Modify: `crates/ferrumd/src/jobs.rs`, `crates/ferrumd/src/main.rs`, `crates/ferrum-apply/src/main.rs` (the `started` progress line)

**Interfaces:**
- Produces: `GET /api/jobs?limit=N` → `{ jobs: [{ id, kind, status, result, detail, started_at, finished_at }] }`; `GET /api/jobs/:id` → one such object plus `events: [...]`.

- [ ] **Step 1: Emit a `started` event from `ferrum-apply run-request`**

In `run-request`'s dispatch, before handing off to the existing subcommand logic, write one line: `progress.event("started", <kind>)` where `<kind>` is the request's own kind string (`"apply"`, `"rollback"`, …) taken from the parsed `request::Request`, not re-derived from the raw file text. This is the only change to `ferrum-apply`'s behaviour in this plan.

Two things this must not disturb, both confirmed real: `is_terminal_line` matches on `event == "complete"` and is unaffected by a new event name; and `Progress::open()` stays silent when `FERRUM_JOB_ID` is unset, so a bare `ferrum-apply apply` typed over SSH still writes no file at all. Add a test asserting the `started` line is the first line of a dispatched job's file, and extend `progress.rs`'s existing "writes nothing without a job id" test if it does not already cover the new call site.

- [ ] **Step 2: Read a job's summary from its JSONL file**

`fn summarize(path) -> Option<JobSummary>`: first non-empty line gives `started_at` (its `ts`) and, if it is a `started` event, `kind`; last non-empty line, if it is a `complete` event, gives `finished_at` plus `result`/`detail` split out of that line's `"<result>: <detail>"` payload (the exact format `Progress::complete` writes — read it rather than assuming). No terminal line means `status: "running"`.

Jobs predating this task have no `started` line; they report `kind: null` rather than failing. A job file that is entirely unparseable is reported with `status: "unknown"` and skipped from nothing — it is real evidence that a real run happened, and hiding it would be worse than showing it plainly.

- [ ] **Step 3: The two handlers**

`GET /api/jobs`: `read_dir($FERRUM_JOBS_DIR)`, keep files whose stem parses as a UUID (**reuse the existing `Uuid::parse_str` discipline `stream_job` already applies for exactly this reason** — the stem becomes a path component), summarise each, sort by `started_at` descending, clamp `limit` to `1..=100` defaulting to 25. A missing jobs directory is an empty list, not a 500.

`GET /api/jobs/:id`: reject a non-UUID id with `400` before touching the filesystem — identical to `stream_job`'s existing guard, and for the identical reason. Return the summary plus every parsed event line.

- [ ] **Step 4: Unit tests**

Real temp directories with real JSONL content: a running job (no terminal line), a succeeded job, a failed job with a detail containing a colon (so the `"<result>: <detail>"` split is proven not to truncate), a pre-`started`-event legacy file, a non-UUID filename that must be skipped, `limit` clamping at both ends, and a `..`-bearing id rejected with `400`.

**Verification:** `cargo test -p ferrumd -p ferrum-apply` passes; clippy clean.

## Task 5: `GET /api/session`

**Files:**
- Modify: `crates/ferrumd/src/main.rs`, `crates/ferrumd/src/auth.rs`

**Interfaces:**
- Produces: `GET /api/session` → `{ username, csrf_token }` or `401`.

- [ ] **Step 1: Return the caller's own session**

`require_session` already validates the session and injects `SessionUserId` into request extensions. The handler needs the session's `csrf_token` as well, which that middleware currently reads and drops. Extend it to inject the CSRF token alongside the user id (a second extension, or widen `SessionUserId` into a small struct — prefer whichever keeps `require_session`'s existing shape clearest), and add an `auth` helper that resolves a user id to a username.

**Read the id and token from what the middleware authenticated, never from anything on the wire** — `require_session`'s own comment states this rule for `POST /api/password` and it applies identically here.

- [ ] **Step 2: Unit tests**

Using the existing in-file test harness that exercises the **real** router (`build_router`, per its own comment — do not re-declare an approximation): no cookie → `401`; a real logged-in session → the real username and a CSRF token that a subsequent real mutating request through the same router actually accepts. That last assertion is the whole point of the endpoint and must not be reduced to "a non-empty string is returned."

**Verification:** `cargo test -p ferrumd` passes.

## Task 6: Static serving and `nix/pkgs/ferrum-ui`

**Files:**
- Create: `crates/ferrumd/src/static_files.rs`, `nix/pkgs/ferrum-ui/default.nix`, `ui/index.html` (a placeholder in this task; Task 7 writes the real UI)
- Modify: `crates/ferrumd/src/main.rs`, `nix/modules/flake/packages.nix`, `modules/core/daemon.nix`

- [ ] **Step 1: The handler**

A fallback service on the router serving `$FERRUM_UI_DIR`, with three rules, each of which gets a test in Step 4:

1. **Never fall back under `/api/`.** An unknown `/api/` path returns `404` with no body — a JSON client silently receiving an HTML page is a genuinely confusing failure and the daemon has one chance to get it right.
2. **Fall back to `index.html`** for any other unknown path, so client-side hash routing survives a refresh.
3. **Reject traversal by canonicalisation** — resolve the requested path, canonicalise it, and confirm it is still under the canonicalised root. Not by string-matching `..`, which misses encoded and symlinked forms.

Static files are served **without** a session (`ui/` holds nothing secret and requiring auth to fetch the login page is circular). Attach it as a router fallback outside the `protected` group, and add a comment saying so explicitly, because "why is this route unauthenticated" is the first question a future security review will ask.

- [ ] **Step 2: The package**

```nix
pkgs.runCommand "ferrum-ui" { } ''
  mkdir -p $out/share/ferrum/ui
  cp -r ${../../../ui}/. $out/share/ferrum/ui/
''
```
Expose it as `packages.ferrum-ui` alongside the existing entries in `nix/modules/flake/packages.nix`. No node, no npm, no fixed-output hash, nothing to regenerate on a dependency bump — that is the whole point of the stack choice and it belongs in a comment on the derivation.

- [ ] **Step 3: Wire `FERRUM_UI_DIR`**

`FERRUM_UI_DIR = "${pkgs.ferrum-ui}/share/ferrum/ui";` in `modules/core/daemon.nix`'s `environment`.

- [ ] **Step 4: Unit tests**

A real temp directory with a real `index.html` and a real nested asset: the asset is served with the right content type; an unknown non-API path returns `index.html`; an unknown `/api/` path returns `404` and **not** HTML (assert the body, not just the status); `../../etc/passwd` in every encoding you can construct is rejected; a symlink inside the root pointing outside it is rejected.

**Verification:** `cargo test -p ferrumd` passes; `nix build .#ferrum-ui` produces the expected tree.

## Task 7: The UI

**Files:**
- Create: `ui/index.html`, `ui/app.js`, `ui/api.js`, `ui/forms.js`, `ui/style.css`

This is the largest task and the one with the least mechanical verification behind it (known risk 1: no type checking). Build it in the order below and confirm each view against a real running daemon before starting the next — not all five files at once.

- [ ] **Step 1: `api.js` — the single place that talks to the daemon**

One function per endpoint. Every mutating call attaches the CSRF token from `GET /api/session` as the header `main.rs`'s `CSRF_HEADER` names (read the real constant; do not guess the header name). A `401` from any call drops the app back to the login view rather than surfacing a raw error — a session expiring while a tab is open is an ordinary event, not a fault.

- [ ] **Step 2: `forms.js` — the schema renderer**

Walk a JSON Schema node and emit a control per type: `boolean` → checkbox; `integer` → number; `string` with `enum` → select; `string` → text; `array` of `string` → repeated rows with add/remove; `object` → nested fieldset, recursing.

**An unrecognised type renders a visibly disabled field with an "unsupported type" note, and its existing value is preserved untouched in the submitted document.** It must never be silently dropped: dropping it means an operator saves a settings document with that option erased, which is the worst failure this file can have and the reason Task 8's check exists.

Take the schema from `GET /api/catalog`'s embedded `schema` key. Because the app submodule is uniform, there is **one** form definition for all apps — that is the design's central claim, and hand-writing a second per-app form path would quietly abandon it.

- [ ] **Step 3: `app.js` — the four views, hash-routed**

**Login** → `POST /api/login`, then load session + catalog.

**Apps** → the app list from `catalog.apps`, each opening the one shared form. Secrets named by the schema get a write-only password input that `POST`s to `/api/secrets/:name` and afterwards shows only *that a value is set* — never a value, because there is no `GET` and there must never be one.

**Apply** → a diff of the edited document against what `GET /api/settings` last returned, then `PUT`, then a **separate, explicitly-labelled** `POST /api/jobs {"kind":"apply"}`. Writing settings never triggers an apply (1.5a's rule) and the UI must make that visible rather than merely honouring it. Stream progress from `GET /api/jobs/:id/stream`. On load, if `GET /api/jobs` shows a job still `running`, reattach to its stream automatically. On a `409`, name the job that holds the lock.

A `PUT` rejected by schema validation renders the daemon's own `messages.join("; ")` against the fields it names — this is the stale-schema path from known risk 5 and it is the only handling that case gets, because a browser tab cannot prevent the situation.

**Generations** → the list from `GET /api/generations`. `rollbackable: false` shows the daemon's own `reason` and no control.

- [ ] **Step 4: The rollback confirmation dialog**

Its own step because it is its own risk (known risk 4 — the original design doc names getting this wrong as *"how a technically correct product earns a reputation for losing data"*). It names the target generation and its snapshot's `taken_at`, and states in plain operator terms:

- **Reverts:** the system closure (every package and service version) and every app's state directory — databases, settings, libraries.
- **Does not revert:** media files, in-flight and queued downloads, ACME certificates, and Authelia users including any password they have changed since.

Write this as real prose an operator reads, not a field dump. It deserves review as carefully as any code in this phase.

- [ ] **Step 5: `style.css` and `index.html`**

Plain, legible, responsive enough to use on a phone on the same LAN. No framework, no web fonts, no external requests of any kind — the UI must work on a box with no internet, which is a real state during initial provisioning and exactly when an operator most needs it.

**Verification:** every view exercised by hand against a real running ferrumd before Task 8 formalises it.

## Task 8: Checks and the real VM tests

**Files:**
- Modify: `nix/modules/flake/checks.nix`, `tests/daemon-end-to-end.nix`, `tests/daemon-apply-end-to-end.nix`, `.github/workflows/ci.yml`

This project's repeatedly-confirmed lesson applies at full force: at least five real bugs across Phases 1.4a/b/c, plus the `path = [ config.nix.package ]` bug that killed *every* ferrumd-dispatched apply, were caught by really running things and by nothing else. A task that ships this phase on unit tests alone has not tested it.

- [ ] **Step 1: `checks.ui-renders-every-schema-type`**

Following the existing `mkAssertionCheck`/`schemaUniformity` pattern in `nix/modules/flake/checks.nix`: walk the real `modules/lib/settings-schema.json`, collect every distinct type shape it actually contains, and assert each is one `ui/forms.js` declares a control for. Have `forms.js` export its supported set as a single greppable literal (e.g. `export const SUPPORTED_TYPES = [...]`) so the check reads one honest declaration rather than parsing JavaScript.

This is the mechanical guard on "adding an app needs no `ui/` change." Without it that claim decays the first time someone adds an option shape the renderer has never seen, and nothing fails until an operator loses a field. Add it to `ci.yml`'s cheap-checks list alongside `catalog-consistency`, `schema-uniformity` and `sopsfile-are-paths` — it is pure eval, so it belongs in the fast job.

- [ ] **Step 2: Extend `tests/daemon-end-to-end.nix`**

Against the real booted host, after the existing real login: `GET /api/catalog` returns the real built catalog with the real app set and a real embedded schema; `GET /api/generations` reports the generation the VM is really running as `current`; `GET /api/session` returns a CSRF token that a subsequent **real mutating request actually accepts**; `GET /` serves the real UI's real `index.html`; `GET /api/nonexistent` returns a real `404` whose body is **not** HTML.

- [ ] **Step 3: Extend `tests/daemon-apply-end-to-end.nix`**

After the real apply this test already performs: `GET /api/jobs` lists that real job with `kind: "apply"` and `status: "succeeded"`; `GET /api/jobs/:id` returns its real, non-empty event log with the `started` line first; and `GET /api/generations` now reports the **new** generation as current. That last assertion is the honest end-to-end proof that the rollback view would show an operator the truth rather than a stale list.
