## Verdict: a resource and a probable ally, not a competitor — and it is already on NixOS

PMS is documentation. It installs nothing: every installation page is a procedure a human follows.
Its author's automation lives in a separate personal repo he frames as *"Because I extensively use
Ansible, 100% of the answers to these questions are stored in my IronicBadger/infra git repo"* — a
worked example, not a product. It has no dashboard, no state management, no rollback, no SSO and no
DNS automation. The competitive surface against ferrum is zero.

The attention surface is large, and the reason to care is this:

**The canonical guide in ferrum's space now runs ferrum's exact substrate.** Kretzschmar moved his
own media server from Proxmox to NixOS — *"the biggest change this year has been a switch out to
NixOS from Proxmox"*, and NixOS is *"a really solid foundation for the media stack"* with
*"uptime has never been higher thanks to the declarative configurations being self-documenting"*
([blog, 2024-11-30](https://perfectmediaserver.com/blog/2024/11/30/end-of-2024-update/)). The site
now carries a NixOS tech-stack page (dated 2026-06-21) and **two** NixOS installation pages.

His public config ([`ironicbadger/nix-config`](https://github.com/ironicbadger/nix-config), host
`morphnix`, last pushed 2026-09-26) uses **mergerfs + SnapRAID + btrfs + snapper**, and its
`flake.nix` imports both:

```nix
disko.url = "github:nix-community/disko";
nixos-anywhere.url = "github:nix-community/nixos-anywhere";
```

That is ferrum's install mechanism, in the hands of the person who wrote the guide everyone reads.

**And the seam is visible.** `morphnix` configures the *substrate* — mergerfs, SnapRAID, Samba,
Docker, QuickSync — but contains no \*arr, Plex or Jellyfin service definitions. The apps are still
Docker Compose generated by an Ansible role in a different repo. **The gap between his NixOS
substrate and his Ansible app stack is precisely the gap ferrum closes.**

## The storage gap this analysis exposes, which is real

PMS's architecture is **hybrid**, which is more careful than ferrum's design doc credits: ZFS for
data that matters (photos, documents, container appdata), mergerfs + SnapRAID for bulk replaceable
media. The argument against all-ZFS is cost of entry and rigidity — *"vdevs / pools are largely
immutable once created. Adding new drives is hard and removing them is impossible"* — which is why
mergerfs preserves one-disk-at-a-time growth.

The part ferrum must take seriously is the other half:

> mergerfs has **nothing whatsoever** to do with parity. If a drive fails, the data on that drive
> is gone.

ferrum pools with mergerfs and **has no parity story at all** — grepping `modules/`, `crates/` and
the design docs for SnapRAID or parity returns nothing. The entire reason PMS pairs mergerfs with
SnapRAID is that the pool itself provides no fault tolerance whatsoever. A ferrum that ships the
convenience half and omits the survival half is shipping half an architecture, and the guide every
prospective user has already read says so on the mergerfs page itself.

What mergerfs does buy, and is worth stating in ferrum's own docs: it does not stripe, so a failed
disk loses only what was on that disk, and every remaining disk stays independently readable and
portable to any other machine. That is a real property and a good one. It is not parity.

### SnapRAID is cheap on this substrate

`services.snapraid` is a first-class NixOS module and `morphnix` already demonstrates the shape —
`parityFiles`, `contentFiles`, `dataDisks`, and the hard-won part, the exclusion list:
`downloads/`, `appdata/`, `/.snapshots/`, `*.unrecoverable`. Exclude the churning paths or every
sync is enormous and useless.

**One design tension to decide deliberately if parity is added:** ferrum snapshots application state
with btrfs keyed to NixOS generations. `morphnix` excludes `/.snapshots/` from SnapRAID for exactly
this reason. ferrum's snapshot subvolumes must be excluded or parity cost explodes.

And the honest limitation to ship alongside it, in PMS's own words: parity is computed on a schedule,
so **between syncs, new files are unprotected**. Which leads to the single best idea in this analysis.

## What to encode as checks rather than prose

This is the highest-value extraction. Each is hard-won PMS knowledge that a guide can only tell you,
and ferrum can guarantee.

| The knowledge | The ferrum check |
|---|---|
| **Parity staleness** — "until you run the parity sync the file is unprotected" | A dashboard figure: *last sync N hours ago, M GB unprotected*. This is the most useful number PMS structurally cannot give a reader, because PMS does not run on the box. |
| A dropped pool branch degrades silently — the pool keeps working, smaller | Compare live branch count and total capacity against the declared config continuously; surface a red state. This is the steady-state twin of the staleness discipline already recorded for the health view. |
| SMART monitoring | ferrum enables no `smartd` at all. PMS installs `smartmontools` but leaves monitoring to the reader; ferrum can wire it to the dashboard. |
| Drive temperature | `boot.kernelModules = [ "drivetemp" ]`, straight from his config, plus `lm_sensors`. |
| **Burn-in before trusting a disk** — `badblocks -b 4096 -wsv`, SMART long test either side, about a week for 8 TB, destructive. He reports catching a drive that died after 19 hours. | A "prepare new disk" flow that runs it and refuses to add an un-burned-in disk to the pool without an explicit override. **Nobody does this by hand.** A tool that does it for you is a genuine differentiator, not a checkbox. |
| **Batch-correlated failure** — "only purchase one drive per retailer per 3-6 months", mix brands and models | Warn when the pool holds more than N disks of one model, or when serial numbers are suspiciously adjacent. Cheap, surprising, and visibly expert. |
| "RAID is not backup" | If ferrum ships parity, ship the sentence with it. The UI must never imply parity is a backup. |

## Two PMS recommendations ferrum already handles — one of them better

Checked against this repository rather than assumed:

- **`branches-mount-timeout=30`.** PMS recommends it because mergerfs will otherwise pool an *empty
  mount directory* when a branch has not mounted yet. ferrum does not set it and does not need to:
  `modules/core/pool.nix:119` emits `x-systemd.requires-mounts-for=` for every branch, so the pool
  does not mount at all until its branches have. That is a stronger guarantee than a timeout, and
  `modules/core/storage.nix:313-330` documents the same hazard from the seeding side.
- **`minfreespace`.** Already present (`pool.nix:95`), with `minFreeGiB` as an option. His live
  config uses 250G.

## One recommendation that deserves a real decision: `epmfs`

PMS names ferrum's default policy specifically, saying `epmfs` *"can surprise users by concentrating
data on single drives"*, and points at `category.create=pfrd` (percentage-free random distribution)
as the current upstream default, which *"spreads new files across the pool without requiring the same
directory layout to exist on every drive."*

ferrum's `modules/core/options.nix:144` offers only `epmfs | mfs`; `pfrd` is not even expressible.

**This is not naivety on ferrum's part** — the project has already been bitten by and fixed the exact
failure PMS warns about. An `epmfs` tree created *through* the mount has exactly one candidate
branch, which is the "whole library on one disk" state, and `storage.nix` seeds the directory tree on
every branch specifically to give `epmfs` more than one candidate to balance across. The seeding is
what makes `epmfs` behave.

So the real question is whether a hands-off installer should depend on a correct seeding step to
avoid a pathological layout, when a policy exists that does not require the same layout on every
drive at all. Worth deciding on purpose and writing down either way. **A user who reads PMS and then
reads ferrum's option description will notice the disagreement**, so ferrum should have an answer
better than silence.

## Audience: both a channel and a hostile crowd, split along a visible line

The hostile half is real and should not be waved away. PMS's value proposition is *"you are in
complete control of every aspect of your system"*; its NAS comparison rejects OpenMediaVault partly
because a web interface "adds unnecessary complexity compared to command-line configuration"; and
the author's instinct when asked how to manage a box is *learn Ansible*. A reader who has run a
week-long `badblocks` burn-in and hand-tuned their pool policies did not arrive looking for a
hands-off installer. To that person, "no hand-editing config files" removes the thing they came for.

The friendly half is larger:

1. **He converted to NixOS for ferrum's own reasons.** Anyone who followed has already accepted that
   hand-managing a box is the problem rather than the hobby. That reader is pre-sold on the thesis
   and is assembling the implementation by hand because nobody shipped it.
2. **The NixOS pages are the hardest part of the site**, and "NixOS Hard Mode — With Flakes" ends by
   pointing at a personal repo. Someone who bounced off that page is a ferrum user in the exact
   moment of needing ferrum.
3. **PMS has no SSO, no per-app DNS and TLS automation, and no atomic rollback.** ferrum is not
   taking the fun away; it is doing the things a guide cannot automate.
4. **Six years of graduates now maintain snowflake boxes they are afraid to touch.** "Reinstall it
   declaratively, over SSH, without losing your data" is a message aimed squarely at them.

**Positioning that works without picking a fight:** ferrum is the PMS architecture, installed for
you, with the day-two parts a guide cannot automate. Credit PMS as the source of the storage
philosophy, make ferrum's pool look like a `morphnix` pool so a PMS reader recognises it and can drop
to the CLI, and make it trivially possible to graduate *out of* ferrum into hand-managed NixOS. The
"takes the fun away" objection dies the moment a hand-builder sees that ferrum's generated config is
config they would have written.

**One strategic friction to have an answer ready for.** Kretzschmar is Head of DevRel at Tailscale,
and PMS increasingly routes remote access through Tailscale — pitched as replacing the reverse proxy,
the VPN, the firewall and *"kinda"* identity management. ferrum's model — your own domain, real
Let's Encrypt certificates, public Cloudflare DNS, Authelia in front — is philosophically opposed on
the exposure axis. The answer is that ferrum's apps are for households and guests who will not
install a mesh client, and that Authelia in front is the concession to being publicly reachable.

## Documentation craft worth copying

- **Numbered-prefix information architecture**: `01-overview → 02-tech-stack → 03-installation →
  04-day-two → 05-advanced → 06-hardware`. **"Day Two" as a first-class section is the quiet
  masterstroke** — it is the part every other project omits, and it holds backups, remote access and
  the app list.
- **Concept pages before procedure pages.** You learn what mergerfs *is and is not* before being told
  to mount anything. That is why the site survives tool churn, and why people trust it.
- **Willing to say "I was wrong, I switched"**, and willing to name what it does not protect you
  from. The SnapRAID page's honesty about the sync window is the reason the rest is believable.
- **A tested-hardware list is worth doing and a hardware guide is not.** PMS already owns the guide
  and competing is pointless. "ferrum has been installed and verified on these machines" is something
  PMS structurally cannot offer, because PMS does not install anything.
